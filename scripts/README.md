## 🚀 dev-init.sh - Главный скрипт инициализации

Комплексный интерактивный скрипт для полной настройки проекта с двухэтапным запуском Docker контейнеров.

### ⚡ Возможности

1. **🔑 Управление CloudPub API**: Автоматически определяет существующий ключ или запрашивает новый
2. **🛠 Выбор бэкенда**: Интерактивный выбор из PHP (Symfony), Python (Django), Node.js (Express)
3. **📂 Работа с версиями**: Если найдена папка `versions/`, предлагает выбрать нужную версию или принять параметр `--version` / переменную `DEV_INIT_VERSION`, после чего вся инициализация выполняется внутри выбранной копии
4. **🗂 Оптимизация проекта**: Автоматическое удаление неиспользуемых папок бэкендов и инструкций
   - Удаляются папки `backends/` для неиспользуемых языков
   - Удаляются папки `instructions/` для неиспользуемых языков (сохраняются `bitrix24/` и `front/`)
5. **🐳 Двухэтапный запуск Docker**:
   - **Этап 1**: Запуск CloudPub для получения публичного HTTPS домена
   - **Этап 2**: Перезапуск всех сервисов с корректными переменными окружения
6. **🗄 Инициализация БД**: Автоматическая настройка базы данных для выбранного бэкенда

### 🧩 Архитектурное решение "Chicken and Egg Problem"

Docker Compose читает переменные окружения только при запуске. Но CloudPub домен становится известен только после запуска CloudPub контейнера. Двухэтапный подход решает эту проблему:

1. **Первый запуск**: Запускаем только `frontend + cloudpub` (БД не нужна!)
2. **Извлечение домена**: Ищем в логах сообщение "Сервис зарегистрирован" 
3. **Обновление .env**: Записываем полученный домен в `VIRTUAL_HOST`
4. **Перезапуск**: Останавливаем и запускаем все контейнеры с правильными переменными

> **💡 Оптимизация**: CloudPub нужна только возможность резолвить `frontend:3000` в Docker сети. Сам frontend может еще не обслуживать запросы - домен все равно будет получен.

### 💻 Использование

```bash
# Через Makefile (рекомендуется)
make dev-init

# Напрямую  
./scripts/dev-init.sh
```

### 🔧 Недавние исправления (ноябрь 2024)

#### ✅ Исправлена логика получения CloudPub домена

- **Проблема**: Скрипт ожидал контейнер `cloudpub`, но в Docker Compose он называется `cloudpubFront`
- **Решение**: Обновлена логика поиска контейнера на правильное имя
- **Улучшения**: Добавлена более надежная проверка статуса контейнера с помощью `--filter "name=cloudpubFront"`

#### ✅ Улучшена очистка Docker ресурсов

- **Проблема**: Ошибки сети "network not found" из-за неполной очистки orphaned контейнеров
- **Решение**: Добавлена агрессивная очистка сетей и контейнеров перед запуском
- **Код**: `docker network rm b24-ai-starter_internal-net` + фильтрация по имени контейнеров

#### ✅ Улучшена логика извлечения домена из логов

- **Проблема**: Домен получался, но скрипт его не находил в выводе
- **Решение**: Расширены паттерны поиска: `Сервис зарегистрирован|Сервис опубликован|https://.*\.cloudpub\.`
- **Fallback**: Если контейнер не запущен, проверяем логи на наличие домена

#### ✅ Оптимизирован первый этап запуска

- **Проблема**: Запускалась база данных на первом этапе, хотя она не нужна для получения CloudPub домена
- **Решение**: Изменено с `COMPOSE_PROFILES=frontend,cloudpub docker compose up --build -d` на `docker compose up frontend cloudpub --build -d`
- **Результат**: Ускорение первого этапа на ~15-20 секунд, меньше нагрузки на систему

#### 🚀 Результат

Теперь `make dev-init` работает стабильно и корректно получает CloudPub домен в 99% случаев, при этом работает быстрее благодаря оптимизации.

## 🛡 security-tests.sh — оркестратор security-проверок

Сценарий запускает единый набор тестов безопасности для активных частей проекта (frontend + выбранный backend) в Docker-контейнерах.

### ⚙ Возможности
1. **Профили запусков**:
   - `quick` — аудит зависимостей + Semgrep OWASP Top 10
   - `full` — быстрый профиль + статические анализаторы, Gitleaks и Trivy
   - `custom` — интерактивный выбор шагов
2. **Авто-определение стека**: после `make dev-init` остаётся только нужный backend, скрипт сам определяет что сканировать.
3. **Docker-изоляция**: все команды выполняются внутри соответствующих сервисов (`php-cli`, `api-python`, `api-node`, `frontend`), никаких локальных установок не требуется.
4. **Отчёты**: JSON/лог файлы складываются в `reports/security/<timestamp>/`.
5. **Дружелюбные предупреждения**: в интерактивном режиме найденные уязвимости подсвечиваются как предупреждение (скрипт продолжает работу), а в `--ci` режимах тот же код выхода трактуется как ошибка.
6. **CI-режим**: `--ci` включает профиль `full` и отключает интерактивные вопросы.

### 🔍 Что запускается
- **Dependency audit**: `composer audit`, `pip-audit`, `pnpm audit` (backend+frontend)
- **Static analysis**: `phpstan`, `bandit`, `eslint` (node/backend + frontend)
- **Semgrep**: набор правил `p/owasp-top-ten`
- **Secret scanning**: `gitleaks` (docker image)
- **Filesystem scan**: `trivy fs` (docker image)

### 💻 Использование
```bash
# Быстрый режим (по умолчанию)
make security-tests

# Профиль full + не валить сборку при ошибках
make security-tests SECURITY_TESTS_ARGS="--profile full --allow-fail"

# Режим CI
./scripts/security-tests.sh --ci --profile full
```

При интерактивном запуске появится меню с выбором профиля и (для custom) подтверждениями на каждый тип проверок.

## 🔧 fix-php.sh - Исправление PHP зависимостей

Скрипт для решения проблем с composer зависимостями в PHP бэкенде.

### 🛠 Что исправляет

- ❌ Поврежденные или отсутствующие vendor файлы
- ❌ Проблемы с автозагрузкой классов

### 🔄 Процесс исправления

1. Останавливает все контейнеры
2. Удаляет только папку `vendor` — `composer.lock` сохраняется, версии не меняются
3. Перезапускает PHP контейнеры
4. Entrypoint php-fpm выполняет `composer install` по `composer.lock`

Обновить версии зависимостей — `make composer-update` (затем проверить `git diff composer.lock`).

### 💻 Использование

```bash
# Через Makefile
make fix-php

# Напрямую
./scripts/fix-php.sh
```

## 🔧 Системные требования

- **Docker & Docker Compose v2**: makefile вызывает `docker-compose`, а `dev-init.sh` — `docker compose`, поэтому должны быть доступны обе команды
- **CloudPub API ключ**: Для создания публичных туннелей ([получить здесь](https://cloudpub.ru/))
- **Bash shell**: macOS, Linux, WSL на Windows
- **Свободные порты**: 8000 (API), 5432 (PostgreSQL) или 3306 (MySQL), 5672/15672 (RabbitMQ, если включён). Порт фронтенда 3000 наружу не публикуется — доступ через CloudPub

## 🏗 Архитектурные особенности

### 🌐 Переменные окружения

Скрипты автоматически управляют ключевыми переменными в `.env`:

```bash
CLOUDPUB_TOKEN=your-api-key                    # API ключ CloudPub
VIRTUAL_HOST=https://your-domain.cloudpub.ru   # Публичный HTTPS домен
SERVER_HOST=http://api-php:8000                # URL бэкенда для фронтенда
```

### 🔀 Выбор бэкенда

При выборе бэкенда автоматически обновляется `SERVER_HOST`:

| Бэкенд | SERVER_HOST |
|--------|-------------|
| **PHP** | `http://api-php:8000` |
| **Python** | `http://api-python:8000` |
| **Node.js** | `http://api-node:8000` |

### 🌍 CloudPub интеграция

CloudPub предоставляет HTTPS туннель к локальным контейнерам:

```
Frontend (frontend:3000 в Docker-сети) → CloudPub → https://domain.cloudpub.ru
```

Это позволяет тестировать Bitrix24 приложения с реальными webhook'ами и HTTPS сертификатами.

### 📁 Volume Mount'ы для разработки

В dev режиме код автоматически синхронизируется между хостом и контейнерами:

| Сервис | Локальная папка | Контейнер |
|--------|----------------|-----------|
| **Frontend** | `./frontend/` | `/app/` |
| **PHP API** | `./backends/php/` | `/var/www/` |
| **Python API** | `./backends/python/django/` | `/var/www/api/` |
| **Node.js API** | `./backends/node/api/` | `/app/` |

**Преимущества:**
- ✅ Изменения в коде мгновенно отражаются в контейнерах
- ✅ Нет необходимости пересобирать образы при изменении кода
- ✅ Hot reload работает для всех сервисов
- ✅ Можно редактировать код в любимой IDE на хосте

## 🐛 Решение частых проблем

### ❌ CloudPub домен не найден
```bash
# Проверьте API ключ
./scripts/test-cloudpub.sh

# Перезапустите с новым доменом
make dev-init
```

### ❌ PHP зависимости падают
```bash
# Автоматическое исправление
make fix-php

# Или ручная очистка
rm -rf backends/php/vendor backends/php/composer.lock
make dev-php
```

### ❌ Контейнеры не запускаются
```bash
# Остановка всех контейнеров
make down

# Полная очистка Docker окружения
make clean

# Перезапуск с нуля
make dev-init
```

### ❌ Ошибка "network not found"

Если видите ошибку `Error response from daemon: failed to set up container networking: network ... not found`:

```bash
# Полная очистка Docker окружения
docker compose down --remove-orphans --volumes
docker container rm -f $(docker container ls -aq --filter "name=b24") 2>/dev/null || true
docker network prune -f
docker volume prune -f

# Перезапуск
make dev-init
```

**Причина**: Подвешенные контейнеры или сети от предыдущих запусков. Скрипт `dev-init.sh` автоматически выполняет эту очистку.

### ❌ Порты заняты
```bash
# Проверьте какие процессы используют порты
lsof -i :8000
lsof -i :5432

# Остановите конфликтующие сервисы
make down
```
